# DMS

DMS is a personal learning project from FoPa Labs: a minimal document management system with hybrid RAG search and an agentic assistant, built to explore ASP.NET Core and local embeddings. It is not a commercial product.

> **Status:** early. Sprint 1 (solution skeleton, schema, CI, local orchestration) is in progress;
> there are no user-facing features yet. See the [sprint plan](docs/planning/sprints.hu.md) (Hungarian).

## Running locally

### Prerequisites

- [.NET SDK 10](https://dotnet.microsoft.com/download) (the exact version is pinned in [`global.json`](global.json))
- [Docker](https://docs.docker.com/get-docker/) (PostgreSQL runs in a container, locally and in the tests)

### Start the stack

```bash
dotnet run --project src/Dms.AppHost
```

This uses [.NET Aspire](https://learn.microsoft.com/dotnet/aspire/) to start, in order:

1. **PostgreSQL** with pgvector (`pgvector/pgvector:0.8.7-pg17`) in Docker,
2. **migrations**: a one-shot service that applies the EF Core migrations, then exits,
3. **api** and **worker**, once the migrations have completed.

The console prints a login URL for the **Aspire dashboard** (`http://localhost:15180/login?t=…`).
The dashboard shows each service's state, logs, traces and metrics, and the API's address.

The first start pulls the PostgreSQL image, which takes a while. The database container is kept
running between runs, with its data in a Docker volume, so later starts are fast and data survives.
Its password is generated by Aspire and stored in the AppHost's
[user secrets](https://learn.microsoft.com/aspnet/core/security/app-secrets), not in the repository.

### Reset the database

Stop the AppHost, then find the container and the volume Aspire created for this project
(both carry the same hash, e.g. `postgres-66f15f13` and `dms.apphost-66f15f13ba-postgres-data`):

```bash
docker ps -a --filter "ancestor=pgvector/pgvector:0.8.7-pg17" --format "{{.Names}}"
docker volume ls --filter "name=dms.apphost-" --format "{{.Name}}"
```

Remove them by name with `docker rm -f <container>` and `docker volume rm <volume>`.

The next start creates an empty database and applies all migrations again.

## Tests

```bash
dotnet test
```

- **Unit tests** need nothing but the SDK.
- **Integration tests** start their own PostgreSQL container with [Testcontainers](https://dotnet.testcontainers.org/),
  so Docker must be running. Each test gets its own database, created from a migrated template.
- **Architecture tests** enforce the project dependency rules.

Tests never call a real LLM or external embedding API. CI ([GitHub Actions](.github/workflows/ci.yml))
runs the same build and tests on every pull request.

## Database migrations

```bash
dotnet tool restore     # installs dotnet-ef from the local tool manifest
dotnet ef migrations add <Name> --project src/Dms.Infrastructure --startup-project src/Dms.Infrastructure \
  --output-dir Persistence/Migrations
```

Migrations are applied automatically by the migration service when the AppHost starts.

## Use of AI

This project is developed with an AI coding assistant (Claude Code). The split is deliberate: the
areas that are the point of the project (embedding pipeline, hybrid search, job queue, agent loop,
chunking, prompt-injection defences) are written by hand; infrastructure, configuration, test
scaffolding and first drafts of documentation may be AI-generated and are reviewed before merging.
Every line is understood and can be explained. The rules are in [`CLAUDE.md`](CLAUDE.md).
